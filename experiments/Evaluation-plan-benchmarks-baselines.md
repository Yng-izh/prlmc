# 评测方案：三个 benchmark + 五个外部 baseline（后续方案文档）

状态：**规划中**。本文档为后续评测的方案记录，尚未执行；各方法的公平性验证（尤其 M+ 与 ReST-KV）未完成。

## 一、三个数据集的选择

| 数据集 | 推荐评测任务 | 选择理由 | 主要风险 |
|---|---|---|---|
| LongBench（ACL 2024） | 六个英文 QA 任务 | MemoryLLM 和 M+ 已报告结果，可作为可信的复现与横向比较基准 | 很多样本不会触发融合 |
| LooGLE（ACL 2024） | shortdep_qa、longdep_qa | 真实长文档，文档超过 24k tokens，考察局部事实和跨段落信息关联 | 部分文档仍低于 50-block 触发阈值；评分协议较复杂 |
| LongBench v2（ACL 2025） | 官方中等长度组（32k–128k words），重点关注文档 QA | 真实长文档、公开答案、标准四选一准确率，更容易保证发生多次融合 | 难度大，评测成本明显高于前两者 |

来源：LongBench 官方仓库、LooGLE 官方仓库、LongBench v2 官方页面。

### 三个 benchmark 在论文中分别回答什么问题

- **LongBench** — 标准性能比较：证明方法没有因引入融合而损害常规长文本 QA。
- **LooGLE** — 真实长文档知识保持：验证跨多个文本块的信息保留与关联。
- **LongBench v2** — 有限容量下的多轮压缩压力：验证长文档超过记忆容量之后的方法有效性。

**关于 LongBench v2 Medium 组**：中等长度组是官方定义的长度类别，不是按模型答对率自行筛选的样本。正式论文必须清楚写成 *LongBench v2 – Medium*，不能把该类别成绩冒充整个 503 题 benchmark 的总成绩。它目前属于建议的主评测范围，尚未下载逐条统计实际分词长度。

## 二、五个外部 baseline

组合原则：不全部选 KV-cache 方法，也不全部选架构差异很大的 latent-memory 方法；采用 **2 个潜在记忆系统 + 3 个不同技术路线的强记忆压缩方法**。

| 外部方法 | 代表技术 | 为什么选它 | 当前可行性判断 |
|---|---|---|---|
| 1. MemoryLLM-8B | 原生潜在记忆、随机淘汰 | 我们直接基于它开发，必选 | 原生 50-block 设置最容易落实 |
| 2. M+ | STM + LTM + 学习式检索 | 最接近我们研究问题的强方法，ICML 2025 | 官方实现和权重可用，但严格限制 CPU 长期记忆尚未验证 |
| 3. StreamingLLM | attention sinks + 滑动窗口 | 经典固定缓存持续处理，原生设计就是硬预算，ICLR 2024 | transformers 侧可用 SDPA 落地，不依赖 flash_attn |
| 4. KIVI | KV 量化而非淘汰 | 强对手：相同字节预算下可保存更多历史信息，ICML 2024 | 官方已支持 Llama-3 系列，适合纳入 |
| 5. ReST-KV | 输出重建引导的 KV 淘汰 | ICLR 2026 新方法，比只按注意力分数选择更强 | 有官方代码和 LongBench 入口；实现是 flash-attn2 forward 的 monkeypatch，`flash_attn` 不可用时无法运行 |

对应代码：MemoryLLM / M+、StreamingLLM、KIVI、ReST-KV。

这个组合的优点是不会只拿早期弱方法来比较；特别是 KIVI 和 ReST-KV 都可能成为有竞争力的 baseline。但**不把这两个说成已完成公平性验证**：目前确认了公开论文、代码和总体技术适用性，没有在我们的 GPU 环境中运行它们，也没有验证全部都能严格遵守 50-block 等价容量。

### 两个必须解决的公平性问题

- **M+**：官方长期记忆可以不断积累，即使每次只检索少量信息，也不等于总容量受限。需要检查能否仅通过容量配置和原有淘汰机制限制其全部 STM、LTM、keys 及缓存。如果必须重新发明淘汰算法，不能把改动版冒充原生 M+。
- **ReST-KV**：官方代码主要在 prefill 后压缩 KV。需要确认长文本写入过程中是否临时建立过超过预算的完整历史缓存。若无法在严格在线预算下运行，它只能作为另一种容量协议的参考，不能混入严格等预算主表。
  - **替代方案**：StreamingLLM 已在主表内，ReST-KV 若无法在严格在线预算下运行则退出主表，该技术路线由 StreamingLLM 代表，不另设替代项。

已筛掉的方案：Compressive Transformer、ToMe 自行移植到 MemoryLLM（需要额外训练与结构兼容工作）；HMT、MBC 暂不列为必做（不同编码器和超小压缩记忆库使直接比较更复杂）。

## 三、统一参数

预算统一采用**真实历史信息存储**，而不是对不同架构强制使用相同的 token 数。

| 设置 | 统一要求 |
|---|---|
| 主预算 | 50 blocks（PRLM-C / MemoryLLM） |
| 等价历史存储上限 | **3.125 GiB**（全部方法，包括 CPU/GPU 的持久历史状态） |
| 输入数据 | 官方数据内容、问题与答案保持不变 |
| MemoryLLM | 50 × 256 latent slots，FP16 |
| KV 方法 | 根据实际 K/V 位宽、层数、heads 和元数据折算预算 |
| 输入顺序 | 按原文顺序处理 |
| 查询时机 | 历史文本处理完成后才提供问题 |
| 不允许 | 查询时重新读取已经丢弃的原始长文档 |
| 生成与评分 | 按各 benchmark 的官方评分协议统一 |
| 结果 | 保存总分、真实记忆占用、压缩次数及时间 |

不同模型的固定权重、额外训练成本也要分别注明。跨模型主表比较的是**完整系统**在相同历史存储限制下的效果，并不能单靠这个表证明融合模块本身优于其他模块；这一点仍需要副表中的同 reader、同载体选择对照。

KIVI 使用量化存储时，允许它在相同字节数下保留更多 token——这恰恰是它的方法优势，不应该强行限制成和 MemoryLLM 相同的 12,800 latent slots。
